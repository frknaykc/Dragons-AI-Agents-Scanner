# Dragons AI Agent Scanner

Local-first, static security scanning of selected AI agent artifacts. See [IDEA.md](IDEA.md) for the broader product vision and [AGENTS.md](AGENTS.md) for contributor safety rules.

Development detection-quality measurements (not unit-test pass rates or a production gate) are documented in [benchmarks/README.md](benchmarks/README.md). The source-only offline runner reports corpus-specific precision, recall, F1, rule support, and explicit false positives/negatives for separate development and holdout splits; it does not change normal scanning or bundle the corpus.

## Current scope

`dragonscan scan PATH` accepts a local file, directory, or supported local archive. It recognizes `SKILL.md`, `AGENTS.md`, `SOUL.md`, `MEMORY.md`, `CLAUDE.md`, `mcp.json`, `.mcp.json`, `mcp-config.json`, and `claude_desktop_config.json` (case-insensitive). Within `.claude`, `.codex`, `.cursor`, `.gemini`, `.windsurf` and `.openclaw` trees it also recognizes `config`/`settings` JSON, YAML or TOML files and `hooks.json`; `.claude-plugin/plugin.json` is plugin metadata. Python/Node dependency manifests and supported lockfiles are recognized by name in local directory scans (see below). Explicit `config`/`settings` files are accepted even without ecosystem context. Other unrelated JSON/YAML/TOML files are ignored in directory scans; explicit unsupported files produce an error. Ecosystem is reported for recognized Python/Node dependency artifacts or when an agent directory context identifies it; `package.json` under `skills/` retains its previous agent ecosystem classification. A generic config with a top-level `mcpServers` object is reclassified as MCP configuration after parsing.

Files are read locally as UTF-8, up to 1 MiB each; symlinks and binary/NUL data are rejected. Markdown, JSON, YAML, TOML and selected line-oriented dependency files are parsed as inert data; neither fenced code nor MCP commands are run by default. YAML aliases and unsafe tags are rejected, and structured nesting/node counts are bounded. Malformed files generate scan errors, not security findings. Default scanning does not fetch URLs, launch servers, execute decoded payloads, or install referenced packages. Bounded Base64/hex content may be decoded in memory for static matching only. Detections are **static indications**, not proof of compromise or execution. An exceptional, separately consented local MCP process inspection is described below.

Built-in detections retain `DAAS-001` (credential file read linked to an external send) and `DAAS-002` (MCP download piped into a shell). New `DRAGON-*` IDs cover instruction override and security bypass (`PI`), sensitive-data access (`CRED`), linked source-to-external-sink transfers (`EXFIL`), instructed download-to-shell execution (`EXEC`), modification of persistent agent guidance (`PERSIST`), promotion of remote instructions to policy (`TRUST`), bidirectional format controls and Base64 decode-to-shell (`OBF`), and static MCP exposure, metadata influence and mutable runtime references (`MCP`). `DRAGON-PATH-001` is an explicitly loaded artifact with a linked sensitive-read → external-send instruction; `DRAGON-PATH-002` is an explicitly loaded fetch-to-shell instruction or MCP configuration; `DRAGON-PATH-003` is remote policy accepted in the same actionable instruction that targets a resolved persistent agent artifact; `DRAGON-PATH-004` is the analogous agent/MCP configuration target. Each finding has a separate severity (potential impact) and confidence (evidence strength); the overall risk is the highest finding severity, not a probability score. Sensitive access alone is lower severity than an explicitly linked transfer. Findings include the affected artifact and available line, a bounded explanation, sanitized evidence and, where applicable, generic source/sink labels. Reported URLs and credential values are never copied into finding evidence.

```sh
uv sync
uv run dragonscan scan ./AGENTS.md
uv run dragonscan scan ./AGENTS.md --format json
uv run dragonscan scan . --format sarif --fail-on high > dragons.sarif
uv run dragonscan scan ./agent --fail-on high
uv run dragonscan scan ./agent --signature-pack ./local-signatures
```

Exit code 0 means the scan completed (findings may be present) without failing an explicitly requested gate. `--fail-on critical|high|medium|low|info` opts into exit 1 if a security finding meets or exceeds that severity; without it, findings alone do not change the exit code. Exit 2 means invalid CLI usage (Click); exit 3 means an operational scan failure, blocked or partial acquisition, or degraded analysis. Exit 3 takes precedence over the security gate: partial analysis is not a clean pass even if SARIF contains findings. Reports are written to stdout before the gate exit; shell redirection still writes `dragons.sarif` when exit 1 or 3 occurs. Use the command's exit status separately from the output file. This changes the previous default `high` gate and separates the former shared exit 2 for usage and operational issues.

## Distribution (not published)

The package is `dragons-ai-agent-scanner` (Python 3.12+); its console command is `dragonscan`. Once published to a Python index, use `uvx --from dragons-ai-agent-scanner dragonscan scan .` (or `uvx --from dragons-ai-agent-scanner dragonscan --help`). For local/offline use, build with `uv build --offline --sdist --wheel` and install the wheel with `uv pip install --offline --python /path/to/venv dist/*.whl`. Neither installation nor ordinary static scanning installs dependencies declared by the scan target. No PyPI release exists yet.

Build the local Docker image with `docker build -t dragonscan:local .`; scan with `docker run --rm --network none -v "$PWD:/target:ro" dragonscan:local scan /target --format sarif`. The Dockerfile uses a pinned Python 3.12.12 multi-platform base manifest, installs only this project's locked runtime dependencies from its own source, and runs as UID/GID 65532. Its allowlisted build context excludes local credentials, tests, reports, Git history and caches. Runtime filesystem access to mounted targets depends on host permissions (non-root cannot read private files); do not change to a writable mount just to work around this. Docker is **not** a security sandbox: do not grant optional dynamic MCP execution on untrusted input. The image has not been pushed to any registry.

Standalone binaries are built on each supported host with `uv sync --locked --group standalone` and `uv run --locked --group standalone python scripts/build_standalone.py`; the build-only PyInstaller version is pinned in `pyproject.toml` and `uv.lock`. Native hosts: Linux x86_64, macOS arm64/x86_64 and Windows x86_64. The executable has the same `dragonscan` subcommands and opt-in behavior; `python -m scripts.smoke_standalone` checks local JSON/SARIF and the security gate. `python -m scripts.checksums dist` writes sorted SHA-256 lines for recognized versioned binaries; the workflow requires all four binaries before generating its checksums. Hashes demonstrate integrity of downloaded bytes, **not** origin or authenticity. No binaries are published yet. The tag/manual [distribution workflow](.github/workflows/distribution.yml) builds and tests on separate native runners, then stages only the verified binary from each runner and `SHA256SUMS` as short-lived workflow artifacts; it does **not** create a GitHub Release or publish packages/images. GitHub workflow artifacts do not preserve executable permissions; on Unix, restore the executable bit after download before running a binary. The project version in `pyproject.toml` is the single artifact-version source; native executable bytes are not claimed to be reproducible.

Default scans in all channels are local and execution-free. HTTPS acquisition (`--remote`), OSV (`--vuln-check`) and semantic analysis (`--semantic`) still require explicit flags and network access; HTTPS uses Python's verified platform trust store (the container inherits its base image CA store). Standalone TLS and optional feature behavior on other hosts need native runner verification. `--installed-agents` uses the runtime's actual home and may have limited visibility inside a container; dynamic MCP remains separately consented and is not a sandbox, including in a bundled binary. No distribution channel silently enables these features.

## SARIF output

SARIF 2.1.0 (`--format sarif`) emits a single JSON document on stdout with `tool.driver.rules` and `results` for actual security findings only. Each emitted rule is derived from its finding metadata, not a separate registry; IDs remain `ruleId`. Critical/high map to `error`, medium to `warning`, low/info to `note`. Known positive source lines are included; no columns are invented. Ordinary files beneath the current working directory have relative URIs for repository-based Code Scanning; external local paths use file URIs. Archive members retain logical `!` provenance in non-repository file/HTTPS URIs, not invented repository paths; GitHub may not link those locations to source lines. Context-dependent signatures have per-result levels rather than a misleading rule-wide default. The projection redacts known credential patterns before bounding messages/descriptions and omits unsafe source URIs; arbitrary unrecognizable secret strings cannot be guaranteed absent. Operational diagnostics do not become SARIF results; use JSON or terminal output for their details. This command does not upload SARIF to GitHub.

## GitHub Action (static checkout scan)

Copy [the example workflow](examples/dragons-action.yml) into the repository to scan, and replace `<commit-with-action>` with an immutable commit of `frknaykc/Dragons-AI-Agents-Scanner` that contains `action.yml` (this milestone is not yet published). `actions/checkout` must run first; the Action does not checkout a repository. The example pins checkout by commit and disables persisted Git credentials. The default `target: .` scans only a path within `GITHUB_WORKSPACE`; absolute paths outside it, traversal, symlink escapes, remote URLs and shell-like expansion are rejected. The Action scans checked-out contents, not a separately authenticated remote target. Use a trusted, pinned Action source rather than `uses: ./` from an untrusted pull-request checkout: the Action's own installation builds its own source, never the target's dependencies.

The composite Action installs a pinned uv version, then uses this Action's `uv.lock` and source to install Dragons in the runner's temporary directory. It never installs target-repository manifests or executes their scripts, build hooks, Git hooks, MCP servers or agent hooks. Inputs are passed through environment variables and Python subprocess arguments, not interpolated into a shell command. No `--dynamic-mcp`, semantic analysis, OSV lookup or remote acquisition is enabled. The scanner itself is static/execution-free by default; setup/install and optional SARIF upload require network access.

`fail-on` defaults to unset: findings alone do not fail the job. Explicit `fail-on: high` forwards `--fail-on high` to the CLI, with no Action-level severity logic. The `exit-code` output retains CLI codes: 0 complete/gate passed, 1 security gate failed, 2 invalid usage/input, 3 operational failure/partial analysis. `sarif-path` points to a runner-temporary SARIF file when produced, including exit 1 or 3. The Action uploads that file only with `upload-sarif: 'true'`, using GitHub's pinned `upload-sarif` Action before restoring the Dragons exit code. An upload failure is a separate failed step; it cannot mask a scan gate failure. The Action does not pass a GitHub token to Dragons or implement a GitHub API uploader.

Set workflow permissions to `contents: read`; add `security-events: write` only when enabling Code Scanning upload. Fork pull requests may not receive upload permission, so opt out of upload or handle the event in a separately reviewed workflow; the scan itself needs no secrets. Code Scanning linkage for archive/remote logical URIs is limited, and actual GitHub-hosted upload has not been exercised locally. Runner filesystem changes during a scan are not sandboxed; do not run untrusted PR build steps alongside the scanner.

## Archive, Git and remote targets

Local `.zip`, `.tar`, `.tar.gz` and `.tgz` targets are extracted into a scanner-owned temporary workspace and passed through the existing static scanner. `uv run dragonscan scan ./bundle.zip` needs no network access. `uv run dragonscan scan ./repo --git` explicitly scans an existing local Git working tree; it does **not** clone, checkout, invoke Git or fetch submodules/LFS. `.git` internals are excluded by normal discovery. Remote Git repositories are **not supported**: system Git redirects, configuration, helpers, proxies and download limits cannot be contained by this acquisition policy.

`uv run dragonscan scan https://public.example/SKILL.md --remote` explicitly downloads a public HTTPS artifact or supported archive. Local/default scans never infer remote access from content. Public unauthenticated HTTPS on port 443 only; URL userinfo, queries, fragments, other schemes/ports and custom request headers are not supported. DNS results must *all* be public; the selected validated IP is pinned for the connection while TLS verifies the original hostname. Redirects (at most three) are resolved and revalidated, including relative redirects. Parent proxy settings are ignored by this downloader. The socket has an 8-second I/O timeout; the download is streamed and capped at 32 MiB, including when `Content-Length` lies. Remote Git URLs are blocked. Embedded links, Git dependencies and `.gitmodules` inside acquired content never trigger another acquisition.

Archive input is capped at 32 MiB; extraction is limited to 2,048 members, 8 MiB per file, 64 MiB total, 1,024 characters per member path and 16 path components. Unsafe/traversing or colliding member names and symlinks/hardlinks/devices/FIFOs are skipped with `partial` status; a limit stops extraction with `blocked` status, without scanning an incomplete expansion. Malformed archives yield `failed` status. Nested archives are **not** recursively expanded. Archive owner, times, executable and setuid bits are not restored. Only complete downloads are scanned; temporary workspaces are removed after scanning. Acquisition never executes downloaded/extracted scripts, hooks or MCP servers, and never automatically enables dynamic MCP, semantic analysis or OSV lookups. Remote/Git acquisition cannot be combined with `--dynamic-mcp` or `--installed-agents`; other network features still require their own explicit options.

JSON adds `acquisition` (`status`, `kind`, `source`, `diagnostics`) only for acquired targets; `not_required` local scans retain their previous shape. Artifact/finding paths use the logical archive source plus `!` and member path, or the HTTPS URL path, rather than the temporary workspace. URLs with secrets are rejected rather than printed. Partial/blocked/failed acquisition is operational diagnostic (exit 3), not a security finding; safe extracted members may still produce findings on `partial`. No new detection IDs are introduced.

**Limits:** Temporary directories are not a sandbox; local filesystem mutation between validation and write/read (including concurrent path replacement) is not protected by directory-handle isolation. Filesystem quotas, decompression ratio and total wall-clock budget are not enforced separately from the fixed byte/file limits and per-operation socket timeout. Archive parser metadata may consume memory before member-count validation. Unicode/case behavior and filename normalization vary by filesystem (case-fold collisions are conservatively skipped). Local Git content is read from the live working tree, not an immutable commit snapshot; neither branch nor resolved commit is reported. Remote content type is checked by filename eligibility and parser validity, not trusted server headers; a plain file may still contain arbitrary UTF-8 text. No persistent cache or authenticated download is supported.

## Installed agent environments (opt-in)

`uv run dragonscan scan --installed-agents` inspects only known configuration roots under the user's home. `uv run dragonscan scan PATH --installed-agents` additionally scans the explicit target; identical files are scanned once and all discovery origins are retained. Ordinary `scan PATH` does not discover installed agents. A discovered config directory/marker proves only that a local **environment/configuration** was found, not that an agent binary is installed or running.

Supported locations (relative to the home directory): Claude Code `.claude` (`settings.json`, `CLAUDE.md`, `skills`); Codex `.codex` (`config.toml`, `AGENTS.md`, `skills`); Cursor `.cursor` (`mcp.json`, `settings.json`, `rules`); Gemini CLI `.gemini` (`settings.json`, `GEMINI.md`); Windsurf `.codeium/windsurf` (`mcp_config.json`) and `.windsurf` (`settings.json`, `mcp.json`); OpenClaw `.openclaw` (`openclaw.json`, `AGENTS.md`, `SOUL.md`). Cursor and Windsurf also support `Library/Application Support/{Cursor,Windsurf}/User` on macOS, `.config/{Cursor,Windsurf}/User` on Linux, and `AppData/Roaming/{Cursor,Windsurf}/User` on Windows (marker: `settings.json`). These fixed locations do not use environment-variable expansion or search the whole home. Some configuration names (`GEMINI.md`, `mcp_config.json`, `openclaw.json`, and platform-specific `settings.json`) are admitted only through these recognized installed-agent roots; ordinary scan classification is unchanged.

Discovery checks marker names and uses the existing artifact classifier for other recognized files in each root, then hands the bounded artifact list to the normal loading, parsing, detection and reporting pipeline. It never runs binaries, plugins, hooks, shell commands, MCP servers, subprocesses, package managers or network calls. `--installed-agents` cannot be combined with `--dynamic-mcp`; semantic and OSV access still require their own explicit options and privacy consent. No new security finding IDs or provenance-derived graph edges are added. Symlink root/marker components are rejected; symlink entries within a root are skipped. The limits are 12 environment locations, 2,048 directory entries per root, four directory levels below each root, and 256 discovered artifacts overall. A root exceeding a limit is omitted with a diagnostic rather than silently partially scanned. Limits do not apply to a separately specified explicit target, which keeps its existing scanner limits.

Terminal output lists environments and statuses (`discovered`, `not_found`, `diagnostic`) plus root/artifact counts. JSON output adds `installed_agents.environments[]` (`agent`, `root`, `source`, `artifact_roots`, `status`, `diagnostic`) and `installed_agents.artifacts[]` (`artifact`, `scanned_artifact`, `provenance`, `agent`, `environment`, `source`). `scanned_artifact` points to the single scanned path if several origins refer to the same inode. Explicit-target origins use `provenance: "explicit_target"` with nullable agent/environment/source. `not_found` is not a security finding; inaccessible or unsafe roots produce diagnostics and exit 3, independently of findings. Artifact contents and raw config/credential values are not logged by discovery. Detection evidence follows the existing reporting/redaction rules.

Known limits: these fixed paths do not cover redirected/XDG-custom config homes, every version of every agent layout, or a full home crawl; some supported agent files may not match the current artifact classifier. Graph references from discovered artifacts resolve only among scanned files inside the home boundary, even with an explicit target outside home; explicit-only references keep their original target boundary. Dependency analysis retains each artifact's explicit or discovered root boundary. As with ordinary path scanning, concurrent adversarial replacement of parent directories between discovery and file loading is not protected by directory-handle isolation; use a trusted/quiescent local filesystem for adversarial race scenarios.

## Offline signatures and IOCs

`signature_models.py`, `signature_ioc.py`, `signature_packs.py`, `signatures.py` and `signature_graph.py` provide validated definitions, local-only IOC extraction, literal/structural content matching, bounded encoded-content inspection, finding provenance and evidence-only graph annotations. The sole built-in signature, `DRAGON-SIG-001`, identifies an actual PowerShell `-EncodedCommand` invocation in a declared executable MCP command; it does not claim the command ran. `DRAGON-IOC-NNN` and `DRAGON-SIG-NNN` are reserved for new signature IDs; existing detection IDs and Python `Rule.detect(Document)` remain unchanged. No reputation feed or real-world IOC set is bundled.

`--signature-pack DIR` reads only immediate regular `.json` files in an explicitly selected local directory (64 files maximum; 1 MiB per file; 1024 signatures maximum). Each file has a `name` (letters, digits, `_`, `-`), optional `version`, and a `signatures` array. For example, this uses a reserved example domain, **not** a claimed malicious IOC:

```json
{
  "name": "my-local-rules",
  "version": "1",
  "signatures": [{
    "id": "DRAGON-IOC-101", "name": "Example domain", "description": "Local test only",
    "type": "ioc", "category": "test", "severity": "low", "confidence": "high",
    "classification": "informational", "artifact_types": ["mcp_config", "skill"],
    "indicator_type": "domain", "pattern": "bad.example",
    "contexts": ["mcp_endpoint", "documentation"],
    "tags": ["test"], "references": [], "remediation": "Review this artifact."
  }]
}
```

`type` is `ioc`, `content` (case-insensitive literal, **not a regex**), or `encoded-content` (literal in decoded text). IOC types: `domain`, `hostname`, `url`, `ipv4`, `ipv6`, `sha256`, `sha1`, `md5`. Supported contexts: `mcp_endpoint`, `remote_endpoint` (actionable Markdown link), `executable_command`, `instruction`, `code_block`, `documentation`, `artifact_hash`. Unknown/invalid fields, duplicate IDs, malformed IOCs and unsupported YARA definitions produce scan diagnostics, not target findings; an incomplete scan exits 2. JSON object duplicate keys are rejected. Symlinked pack files are not followed. A pack cannot override a built-in/rule/detector ID. No pack commands or URLs are executed or fetched.

Domain/hostname comparisons ignore case; URLs support HTTP(S), normalized host/port/path comparison, and remove URL credentials, paths and queries from *reported evidence*. Opaque paths in MCP metadata are already discarded by the parser, so path-specific IOCs cannot match those endpoints; visible Markdown URLs retain paths for matching. No DNS/reputation lookup occurs. Hashes match indicator text or, only for `artifact_hash`, the already-loaded UTF-8 text representation of a successfully parsed artifact (at most 1 MiB); a UTF-8 BOM is removed by the loader. Binary files, unreadable files and symlinks are not hashed. Hash matches are presence evidence, not file-execution evidence.

Documentation/quoted/example indicators remain low-severity informational findings, even when the pack assigns higher severity; active endpoints and executable commands can keep the pack's validated severity. Findings include a `signature` JSON object with `signature_id`, `signature_type`, `indicator_type`, a safe `matched_indicator`, `pack`, `context`, optional `version` and decoded `representation`. Existing non-signature findings omit that object. Terminal output includes signature source and context. Graph `indicates` edges connect only proven active commands/endpoints at the same source location; they do **not** enter taint propagation. Existing correlated findings may cite a host-wide indicator ID only when their proven path ends at the same host and source location; URL-path-specific hits are excluded from host-level correlation references. An IOC by itself cannot create an exfiltration path.

The signature engine's own Base64 and hex decoding is depth 1, in memory, from selected normalized text regions: at most 4096 decoded bytes per token and 32 decode attempts per artifact; decoded content is never executed or printed. Reaching 256 signature hits, 128 distinct IOC candidates per region/type or the decode-attempt limit produces an incomplete-scan diagnostic. The separate evasion analysis below can supply additional bounded transformed views; artifact hashes are **never** computed from those views. The YARA adapter contract is reserved in `signature_yara.py`, but no maintained cross-platform backend or compiled rules are bundled. Local `.yar`/`.yara` files and JSON signatures of `type: yara` are not loaded or run; normal scanning needs no YARA installation. Binary scanning, online updates and automatic community pack downloads are not implemented.

## Evasion-aware static views

An additional local-only pass inspects actionable Markdown instructions, quoted/fenced examples, source-visible hidden HTML/comments and selected attributes, package.json lifecycle scripts, selected JSON/YAML/TOML instruction-bearing fields, and declared MCP command/tool/prompt/resource text. It creates *analysis views*, never modifies the original `Document`: supported transforms include selected zero-width/bidirectional/confusable characters, narrow Unicode compatibility folding, URL percent/HTML entity and character escapes, bounded literal joining and structurally supported token spacing, and bounded standard/URL-safe Base64 and hex (including byte lists and PowerShell UTF-16LE `-e`/`-en`/`-enc`/`-EncodedCommand`). Missing Base64 padding is recovered only if the decoded text is readable and security-relevant. Depth is at most three, with 128 attempts, 128 regions and 64 derived views per artifact, 12 transformations per region, an 8× expansion ceiling, and a 4 KiB source/decoded-view limit. Unreadable, truncated, or limit-hit input is not a clean bill of health: `errors` records incomplete analysis and the CLI exits 2. A match has an `evasion` JSON object describing the transform chain, source kind and location, sanitized original and canonical shape clues, and verification limits. Existing findings omit this field. Findings retain their original ID; this pass does not create a new detection namespace. Terminal output displays the same provenance without raw decoded text; JSON escapes non-ASCII characters (decoded JSON values are unchanged) to keep bidi/control glyphs from acting on consumers.

Only already-actionable instruction contexts can produce active findings from a transformed view. Structured fields retain their original key context and are not promoted into Markdown instructions; private env/header/token fields are excluded. Quoted code, examples, and hidden HTML remain informational; a transformed example cannot become a command. Single-step reversible views are capped at medium confidence; heuristic confusable/token/shell reconstructions and multi-stage views are low confidence, without adding graph taint. Derived graph nodes/edges are evidence-only (`resolution: "derived"`) and never count as observed local load, execution, or taint edges. Original artifact-hash matches remain tied to the original bytes; the signature engine retains its tested depth-one encoded matching for compatibility. This is best-effort static matching, **not** command execution, decryption, complete parsing of HTML/JavaScript/PowerShell or proof of runtime behavior. Custom encoding alphabets are intentionally unsupported without a deterministic agent-security use case; dynamic variables, expressions, runtime code and arbitrary shell evaluation are also unsupported. It can miss split values, mixed scripts and longer chains, and can misclassify unusual documentation. No embedded URL is fetched or decoded content executed.

## Static MCP security

Recognized `mcpServers` entries are normalized **once** into `Document.servers`. Each server retains its declared name, `stdio`/HTTP/SSE/streamable-HTTP/unknown transport, command and arguments (internally), working directory, remote endpoint, runtime/package/version/pinning, environment/header **names and value origins**, and statically declared tools (name, description, instruction, top-level input-schema fields), prompts and resources. Resource HTTP(S) URIs retain only safe public location; non-HTTP resource URIs retain only their scheme. References, definitions, and safe capability labels are linked into the Agent Attack Graph with provenance. Unknown/omitted metadata is not synthesized. `npx`, `npm exec`, `pnpm dlx`, `yarn dlx`, `uvx`, `pipx`, `python -m`, direct Python/Node/native commands, shells/PowerShell, and visible Docker/Podman/nerdctl `run` image references are classified without launching them. Container tags are mutable; digest references are treated as pinned; version ranges and unversioned packages are mutable. This is not package resolution or image verification.

`DRAGON-MCP-001` flags mutable package/image execution; `002` flags URL userinfo; `003` a literal credential-like environment/header value (without its value); `004` shell interpretation with control operators; `005` remote plaintext HTTP; `006` suspicious declared tool/prompt/resource instructions; `007` explicit tool-to-tool shadowing; `008` stated-purpose/behavior mismatch; `009` a mutable remote metadata source (`toolsUrl`), **not proof of an active rug-pull**; `010` a single tool declaring both credential access and network egress; `011` a remote MCP endpoint configured with a credential header reference; `012` an explicitly ordered sensitive-read → remote-transfer instruction with an evidence-backed graph path. `010` is a capability-combination warning, not proof of transfer; `012` requires linked instruction text and graph edges. Metadata-only capabilities require explicit verbs and objects, never just a tool name. Graph nodes may label filesystem read/write, process execution, network egress, credential access, database read/write, browser control, email sending, cloud control, repository write and persistent-configuration write. Tool-poisoning/shadowing findings require actionable instruction text and an existing target, not mere co-presence or quoted warnings.

Raw `env`/header values, credentials in URLs and opaque endpoint paths are excluded from normalized/report/graph output; the scanner retains only reference/literal and sensitive-name flags. Conventional public MCP routes (`/mcp`, `/sse`, `/api/mcp`, `/v1/mcp`) may be preserved; other endpoint paths, queries and fragments are dropped. Finding evidence is fixed/generic, not copied from untrusted descriptions. Static parser diagnostics do not include artifact content. **Default/static scanning neither launches nor connects to MCP servers**, calls tools, performs protocol handshakes, installs packages, resolves mutable tags, or discovers live tool metadata. The exceptional local process mode below only performs handshake and metadata listing. Declared metadata can be absent, deceptive or change after the scan; language heuristics can miss unusual instructions. No claims of actual exfiltration or server compromise follow from these findings.

## Explicit local MCP process inspection (experimental)

Default scanning remains fully non-executing. On POSIX only, `uv run dragonscan scan /absolute/path/to/.mcp.json --dynamic-mcp --allow-uncontained-mcp --dynamic-mcp-server NAME --dynamic-mcp-executable /absolute/path/to/server` explicitly authorizes **one** matching local stdio server. The executable must exactly match the declared absolute path inside the config's directory; the server name must be unique. No args, declared environment, headers, custom cwd, URL, package runner, shell, symlink or interpreter runner are supported. Relative/ambiguous declarations, incomplete static scans and unsupported platforms yield `blocked` without execution. The CLI flags are trusted operator input, **not** instructions taken from the scanned artifact; never supply them based solely on target text. `--dynamic-mcp` alone does not start a process. Static findings and risk are retained unchanged.

**There is no OS filesystem or network sandbox.** The separate `--allow-uncontained-mcp` flag accepts that the approved executable can read files, start descendants, connect to the network, or perform other side effects *before* any protocol limit stops it. Path checks and the private working directory do not confine it; executable replacement between validation and launch is not prevented. Never enable this option for an untrusted executable on a machine with valuable data or network access. An isolated disposable VM/container with externally enforced egress and filesystem policy is required for actual containment; this mode does not create one. No target-provided environment is passed; the child receives a fixed `PATH`, and its stdout/stderr are not printed. Process groups are killed after inspection, but deliberately detached descendants may survive. There is no hard memory, CPU, filesystem, child-count or network quota.

Phase 1 performs JSON-RPC `initialize` (requiring the supported `2025-03-26` protocol version and server identity) and `notifications/initialized`, then `tools/list`, `prompts/list` and `resources/list` only for advertised capabilities. It never calls tools, gets prompts, reads resources, follows URLs, installs packages, or fetches subsequent pages. Startup is limited to 2 seconds and the whole session to 5 seconds; stdout to 128 KiB, stderr to 32 KiB, each message to 32 KiB, protocol messages to 32, nesting to 20 and listed items to 32 per kind. A size/protocol/timeout/early-exit error is a `failed` diagnostic (exit 2) before any successful list, or `partial` (exit 2) when earlier lists succeeded; both preserve static findings and neither is a security finding. Even a `completed` status means metadata was observed, **not** that the server is trustworthy or safe. Observed item names are untrusted, control-escaped in terminal output, and described separately from declared static metadata. Descriptions are represented only by SHA-256 digests; URI bodies and raw stderr are not retained in reports. JSON adds `dynamic_mcp` (status, isolation, diagnostics, observations) **only when requested**; existing finding IDs, severity, confidence, graph and risk are unchanged. No automatic runtime mismatch/rug-pull verdict or semantic-provider promotion is implemented. Semantic analysis and OSV remain separate opt-ins; neither activates dynamic execution.

## Static dependency and supply-chain analysis

Python: `pyproject.toml` (project dependencies, optional groups, dependency groups and selected Poetry declarations), `requirements.txt`, `requirements.in`, `requirements-*.txt` / `requirements-*.in`, and `uv.lock`. Node.js: `package.json` (dependencies, dev, optional and peer groups), `package-lock.json` and `npm-shrinkwrap.json` versions 2–3, `pnpm-lock.yaml` versions 6 and 9, Yarn classic v1 `yarn.lock`, and `.npmrc` registry metadata. Unsupported lockfile versions (including Yarn Berry) and malformed requirements generate diagnostics, not vulnerability findings. Structured input is bounded and at most 4096 dependencies are retained per file; nested requirements/constraint files are not followed. Version, registry and local-path evidence is limited to statically visible declarations. No dependency tree, transitive resolution or integrity verification is performed.

`Document.dependencies` records normalized ecosystem/name, safe requested specifier, available exact version, source (registry, Git, URL, local path or workspace), pinning, package manager, mechanism, group, source location, provenance, optional lockfile and whether integrity *metadata exists*. Python names are normalized across `-`, `_` and `.`; Node names (including scopes) are case-normalized. The scanner distinguishes exact versions, bounded/unbounded ranges, wildcards, `latest`, absent versions, immutable-looking Git commits, Git tags, branch/unknown refs, mutable URLs, local paths and workspaces. A commit string or hash field is **not** proof that remote bytes were verified; manifest ranges remain ranges even when a matching lockfile records an exact version. Conflicting/duplicate information is diagnostic rather than a vulnerability. Custom npm registries (including scopes), Python requirement index URLs and the supported uv index URL are represented by credential-free origin only; no registry is queried. Local references are classified inside, outside, missing, symlink or unsafe without opening referenced files or traversing outside the scan boundary.

Actionable agent instructions using `npx`, `npm exec`, `pnpm dlx`, `yarn dlx`, `uvx`, `pipx` and selected `pip`/`uv pip install` forms are mapped into the same dependency model as manifests; MCP runtime package metadata is reused, with its existing `DRAGON-MCP-001` warning instead of a duplicate mutable-runtime warning. Quoted/fenced documentation is not interpreted as an installation instruction. Node `preinstall`, `install`, `postinstall`, `prepare` and `prepublish` scripts are inspected only for selected suspicious patterns; the existence of a lifecycle hook alone is not a finding. Python `build-system.backend-path` is flagged as project-local build-code exposure, not evidence that code ran. Existing `DRAGON-EXEC-001` / `DAAS-002` findings for remote download piped to a shell receive a `remote-installer` capability rather than a duplicate supply-chain finding.

New finding IDs: `DRAGON-SC-001` mutable registry declaration (low); `002` mutable remote source (low/medium); `003` mutable runtime package execution (medium); `004` security-sensitive Node lifecycle script (medium/high); `005` local dependency outside/symlink/unsafe boundary (medium); `006` remote dependency installed then executed by the same actionable instruction (high); `007` project-local Python build backend path (low). These are **risks**, not claims of malicious packages or observed execution. Dependency package, source and execution edges in the Agent Attack Graph carry location and parser provenance; external `sourced_from` edges have `resolution: "external"`, not a verified remote origin. They do not turn unresolved or external sources into resolved local taint paths. Supply-chain findings include an optional `dependency` JSON object (ecosystem, package, requested, pinning, source, manager, mechanism, group, `integrity_metadata`, provenance, lockfile, path status and registry), omitted from existing findings; terminal findings show safe package context.

**Dragons does not install, resolve, download, import or execute dependencies during static supply-chain analysis.** By default there is no DNS, registry or OSV/CVE query. Package reputation, typosquatting databases, remote integrity verification and YARA matching are not implemented. Experimental, uncontained local MCP metadata inspection requires both explicit execution flags (above); it never resolves or installs dependencies. Pattern matching cannot establish whether a package is safe, whether a script will run in a specific environment, or whether a recorded lockfile will actually be used. Registry URL credentials, tokens, URL paths, queries and fragments are not printed in dependency findings; do not treat a scan as a secret scrubber for arbitrary untrusted artifact text.

## Optional vulnerability intelligence (OSV)

`uv run dragonscan scan PATH --vuln-check` explicitly enables HTTPS requests to **api.osv.dev** after the local static scan. Only normalized PyPI/npm package names, ecosystem and exact versions are sent. No file content, project paths, credentials, artifact URLs, registry authentication, scripts or prompts are sent; scanned instructions never select a host, route or payload. The HTTP client uses the system HTTPS proxy if configured, rejects redirects and limits each request to 5 seconds and 1 MiB. There is a 30-second scan-level request budget, 256 unique package/version queries, 32 distinct advisory details, and at most 512 resulting findings. No new dependency, automatic retry, persistent cache or background request is introduced; identical package/version queries and advisory detail fetches are deduplicated in memory per scan. An HTTP proxy is part of the operator's network configuration and may observe the destination and requests.

Only statically observed registry packages with an exact version and public/default registry provenance are eligible; custom/private registries, ambiguous indexes, ranges, `latest`, local/workspace paths, Git and URL dependencies are skipped. A declared exact version is **not** proof the package was installed, and a lockfile does not prove that it was used. Unsupported or skipped inputs yield `vulnerability_diagnostics`; no query for an eligible package means `vulnerability_status: "skipped"`. A successful complete response is `"complete"`; malformed, rate-limited, timed-out, truncated or unavailable OSV data produces `"partial"` and CLI exit 2, while preserving all local static findings. Skipped individual dependencies are not asserted safe. The pre-existing `--fail-on` severity threshold still controls exit 1 if the scan is otherwise complete. Without the flag, `"disabled"` is reported and no provider is constructed.

OSV `querybatch` supplies version-match IDs; `/v1/vulns/{id}` supplies bounded details, checked against the queried ecosystem/package. `DRAGON-VULN-001` (low for dev/optional/peer/lockfile, otherwise medium) reports the advisory as a dependency risk. `DRAGON-VULN-002` (high) requires a matching versioned runtime-execution dependency and graph evidence; `DRAGON-VULN-003` (high) requires the same version and linked MCP tool with explicit credential-access **and** process-execution signals. Neither establishes exploitation, actual execution nor package compromise. CVSS strings and upstream severity are attributed metadata, **not** Dragons severity scores. New findings include a `vulnerability` JSON object (provider, ID, aliases, package/version, summary, upstream severity, CVSS strings, fixed versions, affected ranges, HTTPS references, published/modified dates, provenance and query status); existing findings omit it. Top-level `vulnerability_status` and `vulnerability_diagnostics` are added to JSON. `Scanner.graph` retains version-qualified `package_version` → `vulnerability` `affected_by` evidence edges after the scan; these are not taint-propagation edges, and unrelated versions/remote relationships do not escalate findings.

## Optional threat intelligence

The default `dragonscan scan PATH` is unchanged: it loads no threat feed, performs no feed update, and makes no network request for threat intelligence. No third-party or synthetic malicious corpus is bundled. Load an explicitly selected local JSON feed with `dragonscan scan PATH --intel ./intel.json` (repeatable), or an explicitly selected installed store with `dragonscan scan PATH --intel-store ./my-store`. Feed data is never executed, imported, submitted, or sent to semantic analysis. The official Action does not enable intelligence by default. For Docker, mount the feed read-only and pass its container path to `--intel`; the image has no persistent update store by default.

Schema version 1 is strict: a UTF-8 JSON object with `schema_version: 1`, `feed_id` (safe alphanumeric/`_.-` identity), numeric dot-separated `feed_version`, and `records`. Each record requires `id`, `indicator_type`, `value`, `classification` (`malicious` or `suspicious`), and `source`; optional bounded `description` and HTTPS `reference` are **metadata only**, never fetched. `package` records also require `ecosystem` (`npm` or `PyPI`) and **exact** `version`; `sha256` may specify `artifact_kind` (`skill`, `plugin_metadata`, etc.) to scope an exact raw-file hash. Supported indicators: `domain`, `hostname`, `url`, `ipv4`, `ipv6`, `sha256` (raw bytes of parsed text artifacts), and `package`. For example, this is a **synthetic test-only** record, not an assertion about any real package:

```json
{"schema_version":1,"feed_id":"my-feed","feed_version":"1.0","records":[{"id":"synthetic-1","indicator_type":"package","value":"example-test-package","ecosystem":"npm","version":"1.2.3","classification":"suspicious","source":"Synthetic example"}]}
```

Feeds are capped at 1 MiB, 512 records and 16 explicitly selected files. Fields and candidate counts are bounded; duplicate IDs, indicators, JSON keys, unknown fields/schema, invalid values, control characters and malformed input are rejected. Malformed optional feeds produce a partial intelligence diagnostic while the base static scan continues (CLI exit 3 in the existing incomplete-scan contract), not a security finding. An intelligence hit uses stable `DRAGON-TI-001` and includes feed ID/version, record ID, classification, source and exact indicator context in terminal/JSON/SARIF result properties. The feed cannot choose Dragons severity or confidence: exact file SHA-256 is high severity/high confidence; an exact, pinned package or active IOC is medium severity/medium confidence; documentation indicators are low severity. Feed disagreement/multiple sources do not escalate severity. Matching reuses the existing IOC normalization and extracted regions: no substring, URL prefix, inherited subdomain, hash prefix or name-only Skill/plugin/MCP match. Versioned npm/PyPI identity requires a statically parsed exact registry declaration or pinned MCP package. A match is **not observed malicious behavior**, an infection verdict, or proof that a package was installed; it adds no taint, graph attack, or execution edge.

Updating is a **separate explicit operation**: `dragonscan intel update --url https://PUBLIC-HOST/feed.json --sha256 EXPECTED_SHA256 --store ./my-store`. The URL and expected digest must come from the operator, not the downloaded feed. The existing public-HTTPS/SSRF/redirect/TLS/proxy download policy applies, bounded to 1 MiB. A downloaded candidate is size-limited, SHA-256 checked, strictly validated and atomically installed as `intel.json` in the chosen store; malformed feeds, mismatches and numeric-version downgrades preserve the previous valid feed. No background refresh/freshness lookup occurs; stale feeds remain usable offline. SHA-256 confirms the bytes against the **operator-supplied digest**, not publisher authenticity; there is no feed signing or publisher authentication. Operational update failure exits nonzero and does not create a scanner security finding. The store is local and explicit (not silently loaded from the home directory); existing world-writable stores and symlink path components are rejected for updates. Path-handle TOCTOU against a concurrently hostile local user is not fully prevented; place the store in a trusted user-owned directory.

Feed files are reloaded for each scan (including when reusing a `Scanner` instance); removed or corrupt installed feeds do not leave cached matches. `source` is treated as a display label: URLs, credential-like values and unsafe labels are replaced with `<redacted>` in terminal, JSON and SARIF output. Optional references are validated but never fetched or included in findings. This is best-effort secret protection, not a guarantee that arbitrary opaque strings are recognized as secrets.

## Development

Python 3.12+ and `uv` are required. `uv.lock` records resolved dependencies.

```sh
uv run pytest
uv run ruff format --check .
uv run ruff check .
uv run mypy src
```

The scanner pipeline is in `src/dragonscan/`: discovery/classification, bounded loading, format-dispatched parsing into `Document`, local behavior observation, independent legacy and new detectors (including static dependency analysis), bounded graph construction and correlation, risk aggregation, then terminal/JSON reporting. `Document` retains Markdown blocks/spans, structured entries with key paths and typed values, MCP server metadata, normalized dependencies and diagnostics, explicit relationships, and source references (path, format and line/range where the parser provides it). JSON/TOML entries and server definitions from those formats have no precise line information; YAML entries and servers retain line ranges. Markdown inline references use their enclosing block's line range. Soft/hard breaks in Markdown instructions retain their line separation. Secret-bearing `env`/header values are not retained in normalized entries; MCP metadata stores their names and value-origin categories, never the values. URLs in MCP metadata are stripped of credentials, opaque paths, query and fragment; a boolean records whether MCP URL userinfo was present. Raw untrusted content is not included in parser diagnostics.

JSON output retains `path` and `kind` for each artifact and adds `source_format` and nullable `ecosystem`. Existing `DAAS-*` IDs, CLI options, and `Rule.detect(Document)` signatures remain supported. `Scanner(rules=...)` selects only those legacy Python rules as before; `Scanner(detectors=...)` may select contextual detectors alongside the default legacy rules. New `EngineDetector.detect(DetectionContext)` takes a document, non-secret observations, and prior findings **from that artifact**. `DetectionMetadata` validates IDs, required fields, impact/confidence/classification and applicable artifact types; `DeclarativeDetector` uses exact observation kinds rather than evaluating an untrusted rule expression. Correlated findings add `path` (ordered objects with `edge`, `source`, `target`, `artifact`, nullable `line`, `origin`, `confidence`) and `taint` (class names). Other findings omit these two keys; existing finding keys remain unchanged. There is no Python rule-file loader or working YARA backend in this release. Custom `Rule.artifact_types` values should use the `ArtifactKind` string values (`skill`, `memory`, `soul`, `agent_config`, etc.). Tests materialize inert corpus strings under exact artifact filenames in pytest temporary directories; never execute or install their contents. Source distributions exclude tests and test artifacts.

### Static Agent Attack Graph

`attack_graph.py` builds nodes for scanned artifacts (including skills), actionable instructions, MCP servers, declared tools/prompts/resources/capabilities, statically identified shell capability, commands, packages, sanitized external endpoints, dependency registries/sources, sensitive resources and persistent targets. Evidence-backed edges include `references`, `loads`, `defines`, `exposes`, `influences`, `authenticates_with`, `invokes`, `depends_on`, `installs`, `sourced_from`, `reads`, `sends_to`, `fetches`, `executes` and `modifies`. Each edge carries a source location, parser/behavior origin, resolution status and confidence. Explicit Markdown load directives and structured `instructionFile`/`skillFile`/`agentsFile`/`configFile`/`skills` references resolve only against **already scanned** local artifacts within the selected target. Plain hyperlinks remain references, not inferred loads. Missing, ambiguous, outside-boundary and symlink references stay unresolved; remote references remain inert external nodes. Single-file scans never expand to adjacent files.

`correlation.py` propagates only supported artifact-level taint classes (credentials, private/SSH/cloud material, API/wallet secrets, sensitive environment/files, untrusted web/remote instructions and persistent control). Paths require an explicit local load plus a linked read-and-send, or a fetch-to-shell instruction/MCP configuration. Remote-policy modification requires the remote trust and single unambiguous target in the **same actionable segment**, with the target scanned and locally resolved. Capability co-occurrence or a bare reference does not imply flow. Path confidence is the lowest confidence among its constituent edges and flow evidence, ordered High → Medium → Low; severity reflects potential impact independently and does not increase merely because there are more files. Existing local findings are retained and their IDs referenced by correlated findings where relevant. Traversal is cycle-safe with a maximum of eight load hops, 256 explored routes, 50,000 graph nodes and 100,000 edges; hitting graph limits reports a scan error instead of silently claiming completeness.

`mcp_correlation.py` adds `DRAGON-MCP-012` only when a declared tool contains one ordered sensitive-read → remote-send instruction **and** the matching observed MCP graph edges exist. The path ends at a static network-egress capability, not a visited endpoint or observed data transfer. MCP resource URLs stay external provenance and are not treated as resolved local taint paths. Explicit `Scanner(rules=...)` selections do not run built-in graph correlation, preserving rule-only selection behavior.

### Advanced static flow scope

`flow.py` maintains independent `sensitive_data`, `untrusted_content`, `instruction_control` and `execution_influence` states. Edge names are assigned data-, control- or execution-propagating, capability-only, provenance-only, metadata-only or non-propagating roles; the role alone never authorizes traversal. Traversal also checks endpoint kinds, resolution, source origin and flow class. In particular, `affected_by`, `indicates`, `observed_version`, `reveals_static_view`, registry metadata, and unresolved/ambiguous/external/outside relationships cannot create taint paths. Source/sink evidence, ordered steps, crossing and transformations appear in the optional `flow` JSON object and terminal summary; original `path`/`taint` fields and detection IDs remain unchanged. Flow confidence is capped by its weakest supporting evidence; severity remains impact-based. Evidence is statically observed instructions and declarations, never proof of execution.

| Detection family | Applicability | Required evidence / limitation |
| --- | --- | --- |
| Sensitive resource → external sink (`DRAGON-PATH-001`, `DRAGON-MCP-012`, `DRAGON-FLOW-002`) | Source / sink; correlated flow findings | Same actionable segment or explicit uniquely resolved tool-result transfer; a bare read and send in separate tools do not suffice. Raw sensitive values are not placed in flow evidence. |
| Local instruction load → remote execution or remote instruction → persistent write (`DRAGON-PATH-002/003/004`) | Source / sink; correlated flow findings | Resolved scanned local artifacts and actionable fetch/execute or same-segment remote-policy-to-write relationship. Unresolved/external links remain provenance, not local propagation. |
| Tool influence (`DRAGON-FLOW-001`) | Control source / privileged sink; correlated flow finding | Explicit ordered shadowing/influence between identified MCP tools and a privileged capability. An instruction that only names an MCP tool creates an invocation reference, not influence. |
| Mutable runtime dependency → execution (selected supply-chain findings) | Package source / command sink; contextual flow | Requires a statically observed runtime install→execute route. Mere registry provenance or a declared package is not enough. |
| Exact IOC (`DRAGON-IOC-001`) | Conditional route enrichment | Indicator must match the specific endpoint on the proven route; same-artifact presence is not enough. General IOC/signature findings remain artifact-level. |
| OSV (`DRAGON-VULN-001/002/003`) | Conditional enrichment for `002`; otherwise contextual | An exact-version runtime install→execution route may enrich `002` after explicit OSV opt-in. `001` is an advisory, not flow. `003` ties an exact version to declared privileged MCP metadata but does not assert package→tool execution reachability; `depends_on` and `affected_by` cannot propagate. Ranges, dev-only packages and mismatched versions do not borrow routes. |
| Evasion-derived findings | View-level confidence, not a taint edge | Single reversible transformation is at most medium; heuristic or multistep reconstruction is low. The original location and transformation remain available, but `reveals_static_view` alone cannot manufacture fetch/execute flow. |
| Other built-in detections (including local signatures, secrets and hardening checks) | Non-flow / artifact-level | Findings are preserved; their co-occurrence is not a source→sink route. No claim that every built-in detection participates in flow. |

Flow exploration limits depth to 8, 32 branches per state, 32 routes per source, 256 total paths and 16,384 states; graph limits are 50,000 nodes and 100,000 edges. Limits and skipped relationships generate diagnostics rather than complete-route claims. OSV is optional, bounded and not queried in default offline scans. Derived transformed views can identify suspicious text but are not promoted into executable graph edges without independent actionable evidence.

This is **static agent-artifact-level flow analysis**, not programming-language taint tracking. It neither evaluates variables/actual MCP tools nor establishes runtime reachability, actual data transmission, installed package resolution or remote content safety. Only unambiguous local, explicit relationships contribute to correlated paths; alternate prose and larger/deeper route sets can be missed. Context filters suppress many quoted/code/negated examples, but static heuristics can still misread unusual prose. Not implemented: remote repository/archive/system scanning, script AST parsing, SARIF/Markdown output, dependency resolution or arbitrary network lookups. By default no URL from a scan target is visited, MCP server started or scanned instruction executed; the separate uncontained MCP metadata-only opt-in described above does not feed static flow analysis.

## Optional semantic analysis

Default scanning remains offline and needs neither model nor key. `uv run dragonscan scan PATH --semantic --semantic-url https://trusted.example/v1/chat/completions --semantic-model MODEL` opts in to bounded, sequential OpenAI-compatible chat completions **after** static analysis. To use a local model server, explicitly set `--semantic-url http://127.0.0.1:PORT/v1/chat/completions` (or `[::1]`); HTTP hostnames including `localhost` and non-loopback HTTP are refused. A key, if required by your server, is read from `DRAGONSCAN_SEMANTIC_API_KEY`; do not put it in an artifact. The model name and endpoint are trusted operator configuration, never scan data. HTTPS uses normal certificate validation; redirects are disabled. Remote HTTPS may use the operator's configured proxy. Semantic mode neither enables OSV nor loads a signature pack, and neither enables semantic mode. There are no new package dependencies.

Selection targets suspicious parsed instructions, same-location static findings and declared MCP tool metadata; it does **not** understand every line in a repository. Candidates are ranked by local static finding impact/count, with stable path/line tie-breaking, deduplicated by a hash of redacted content and safe static context, and never cached across scans. A short source excerpt, bounded same-location detection IDs/categories, candidate task and allowed semantic categories are sent; full raw files, arbitrary tool schemas, flow paths, configured API keys in the request body, full prompts in reports, and previous scan history are not sent. A configured provider key is transmitted to that provider in the authorization header. Credential assignments (including common AWS key names), auth headers, URL userinfo, recognized key formats and private-key blocks are redacted before truncation; incomplete private keys and oversize candidate text are skipped with a partial diagnostic. **Redaction is best-effort, not a guarantee that arbitrary secrets in ordinary prose are removed.** Review target privacy before using a remote provider. There is no web search, browser, tool use, scanned prompt override, file access by the model, or provider-supplied link fetching. Requests tell the model to treat evidence as untrusted data; strict independent schema/evidence validation is the actual control, not that instruction alone.

The fixed categories are `DRAGON-SEM-001` sophisticated prompt injection, `002` MCP tool poisoning, `003` declared MCP metadata mismatch, `004` persistence intent and `005` sensitive-data handling intent. Category `003` requires both a declared tool description and declared tool instructions; it does not establish actual runtime behavior. Provider results must be JSON with `results` entries containing only `category`, `verdict` (`detected`, `likely`, `uncertain`, `not_detected`), `confidence` (`high`, `medium`, `low`), bounded `rationale`, and Dragons-generated `evidence_ids` (`E1`, etc.). Unknown IDs, categories, fields, duplicate keys and oversized output reject that candidate; model-provided severity, URLs and unverified reputation claims are ignored. Only `detected`/`likely` with at least medium confidence yield a finding. Dragons assigns at most **medium** severity when a high-confidence detected result cites a same-location static finding supporting that semantic category, otherwise **low**; classification is `suspicious`. Model confidence remains an attributed opinion, not static proof. At the same artifact **and line**, supported matching deterministic IDs may instead receive `semantic` provenance only when the result cites that finding's evidence ID, without changing its existing severity/classification. Semantic findings do not remove deterministic findings, connect unrelated artifacts, add graph edges, or create taint/flow paths.

Default limits: 16 selected candidates, 16 requests, 2,048 characters of candidate excerpt, 8 same-location static findings, 16 KiB request body, 32 KiB response, 3 model results per candidate, 8 evidence IDs per result, 320 rationale characters, 5 seconds per request and 30 seconds across semantic requests. Other limit fields reserve context/entry/flow budgets; no unrelated context or full flow path is sent in this version. Candidate/request/time/privacy/provider/response exhaustion yields `semantic.status: "partial"`, a diagnostic (not a security finding), and exit 2, retaining completed deterministic results; with no candidates status is `"skipped"`. Successful semantic analysis returns `"complete"`; disabled scans have no `semantic` JSON section and no semantic terminal section. Terminal marks attributed results `SEMANTIC`; JSON adds top-level `semantic` status/provider/model/counts/diagnostics and an optional `semantic` object on findings with candidate ID, task, schema version, verdict, evidence IDs, rationale and transformation provenance. Prior JSON fields and finding IDs remain intact. Because candidate selection and redaction are selective, semantic mode cannot prove the absence of malicious intent. Markdown/SARIF output, multiple providers, cross-scan cache, retries, agent frameworks, autonomous tools and dynamic execution *by the semantic provider* are not supported. The independent explicit local MCP inspection mode does not supply evidence to semantic findings.
