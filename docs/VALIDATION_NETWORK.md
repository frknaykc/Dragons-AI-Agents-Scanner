## Scope and method

- Initial `main` / `origin/main`: `25177cf63f4136971afcab2906bda649c405a8ee`. Observation checkpoint: `ec5231e0f25b367bad82a50ebea0648924d0de2f`. The [dispatch-only workflow](../.github/workflows/network-observation.yml) uses an exact trusted checkout, `contents: read`, no persisted checkout token, no publishing, and no privileged tracing. Four native PyInstaller binaries were built on their respective hosted runner labels and copied outside the checkout. Runtime excludes the project virtual environment from PATH; scans use local, inert fixtures, a clean temporary working directory, no optional online features, and JSON output. The controlled MCP URL and document URL point to loopback and are data, not fetched endpoints. No artifact-supplied command is executed.
- Linux: `strace` 6.8, unprivileged child launch with `-f -ttt -e trace=connect,sendto,sendmsg,sendmmsg`; tracing wraps the complete scan. TCP `connect` and UDP `sendto` loopback controls succeeded and were PID-attributed. This covers traced userspace IPv4/IPv6 connect and addressed datagram operations, including failed attempts; it does not inspect HTTP payloads, prove impossibility of future network access, or independently validate external DNS/IPv6 visibility. Raw syscall traces are ephemeral and never uploaded. [strace manual](https://man7.org/linux/man-pages/man1/strace.1.html).
- macOS 15.7.9 Intel and arm64: `/usr/sbin/lsof -nP -a -p PID -iTCP -sTCP:ESTABLISHED` polling as the runner user. Each held TCP loopback control was detected. This sees only sampled *established* direct-PID TCP sockets, not brief or failed attempts, UDP/DNS, child processes, or HTTP content. DTrace is not assumed available without privilege: Apple documents SIP restrictions, including protected-process DTrace limits ([Apple runtime protections](https://developer.apple.com/library/archive/documentation/Security/Conceptual/System_Integrity_Protection_Guide/RuntimeProtections/RuntimeProtections.html)). Neither privileged tracing nor Network Extension entitlements were used.
- Windows Server 2022: `netstat -ano -p tcp` followed by `Get-NetTCPConnection -OwningProcess PID -State Established` polling, runner user. The loopback client exited 0 and the listener accepted, but neither sampler identified its connection under the launched PID even with an eight-second hold. Therefore **MONITORING STATUS: INVALID**. No scanner offline verdict follows. Event Tracing for Windows session control requires elevation or Performance Log Users membership ([Microsoft ETW access control](https://learn.microsoft.com/en-us/windows/win32/etw/controlling-event-tracing-sessions)); Windows Filtering Platform audit events contain process, direction, address, and protocol but depend on configured auditing ([Microsoft event 5156](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-5156)). Neither mechanism was enabled, and no privilege escalation was attempted. Netstat and PowerShell sampling would be inadequate for failed connections even if the control passed ([netstat reference](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netstat); [Get-NetTCPConnection reference](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-nettcpconnection)).
- All observers are runner-user processes; their positive controls used only controlled loopback sockets. The controls do **not** establish external-network, IPv6, or DNS coverage. Network traffic from build/setup and other runner processes is not attributed to the scanner. No packet-count inference is used.
