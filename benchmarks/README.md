# Detection-quality benchmark (source checkout only)

Run offline from the repository root:

```sh
uv run --offline python -m scripts.benchmark benchmarks/corpus/manifest.json
uv run --offline python -m scripts.benchmark benchmarks/corpus/manifest.json --format json
```

`--format json` includes case-level actual occurrences, FP/FN IDs, per-rule and split metrics, plus independent correctness failures. `--format baseline` prints the compact measured summary; redirect it to `benchmarks/baseline.json` **only after an explicit review**. A normal run never updates the baseline. The command exits 1 when explicit correctness assertions fail, 2 on partial/configuration failure, and 0 for complete evaluations with no correctness failure (even if ID-level quality is poor). This is not a precision/recall release gate. Neither the corpus nor the runner is bundled into the runtime wheel.

## Ground truth and isolation

`corpus/manifest.json` schema 1 is authoritative: each stable case ID declares a local artifact (file or directory), malicious/benign classification, development/holdout split, synthetic/curated/real-world-derived provenance, notes, explicit expected security finding IDs, optional expected categories, occurrence assertions and targeted absent IDs (`expected_absent`), and an optional explicit local synthetic TI feed. Case labels and expected IDs never reach the scanner. Only local targets are permitted; invalid IDs, repeated JSON keys/expectations, missing or escaping paths and symlinks are rejected. Corpus files are **untrusted data**; never execute their contents. A fresh default static `Scanner` is created for each case, with no home-installed TI feed, semantic provider, dynamic MCP, OSV, remote acquisition, subprocess or update. Only listed local TI cases opt into a synthetic feed. The runner never requests network access. Schema 2 invokes only local `git rev-parse HEAD` for optional reproducibility metadata (never a command from an artifact); schema 1 does not invoke subprocesses. There is no OS-level sandbox: these are static API choices, input validation, and regression checks, not a guarantee against an unrelated scanner vulnerability.

`development` is for measurement and subsequent separate tuning; `holdout` should not be changed to tune detectors. It is checked into Git, **not hidden/blind**. In corpus 1.4, holdout artifact bytes, expected positive IDs and splits remain unchanged, but *category* expectations for five case/ID pairs were corrected against emitted categories and two holdout cases gained occurrence assertions **after their behavior was inspected**. Nine original benign cases gained targeted `expected_absent` assertions. Additionally, 26 **development-only** cases were written to cover default-scanner rule families (23 positive, 3 targeted negatives). They were inspected against current scanner behavior and are **regression examples, not independent blind validation**; holdout did not grow. Existing development/holdout near-duplicate checks from 1.1 still apply. Current cases are small, inert, mostly synthetic/locally curated examples; no external malicious dataset or active IOC. `classification=malicious` on a risky configuration means an expected security signal, **not** proof of malicious intent or execution. Reserved `.test` / `.invalid` domains and a documentation IPv4 address are used. The previously missed TI terminal-period IOC is now detected; the previous FN is retained in Git history, not silently carried into the new baseline. A local TI nonmatch is included. No live semantic models (five semantic IDs), dynamic MCP runtime behavior or real-world prevalence are measured.

## Interpretation

The detection metric unit remains **(case, finding ID)**: TP = expected ID present; FN = expected ID absent; FP = actual security ID absent from expected IDs, including extra detections on a malicious case. Repeated locations collapse for **ID scoring only**. Independently, `expected_categories` now asserts the actual category of *every occurrence* of that ID when present. Optional `expected_findings` is an exhaustive list of expected occurrences **for each listed ID**: each actual occurrence must pair uniquely with one expectation; missing, wrong-field and extra occurrences fail correctness without changing ID-level TP/FP/FN. Only fields explicitly present are compared: `category`, relative `artifact`, `line`, substring `evidence_contains`, `source`, `sink`, `severity`, `path_edges`, `path_nodes`, `flow_edges`, `flow_nodes`. `source`/`sink: null` asserts absence; omitted fields are unchecked. Path/flow arrays are exact ordered sequences. An ID with no `expected_findings` is not occurrence-asserted. `expected_absent` tags specific case×ID hard-negative assertions; a hit is both the ordinary ID-level FP and a separately reported hard-negative failure. Category mismatches with absent IDs remain ID-level FN, not an extra category failure. Correctness `checked` counts explicit occurrence and category comparisons; `hard_negative_checked` counts targeted absent assertions. `failed` counts category mismatches, unmatched/wrong/extra occurrences and targeted absent hits (these may overlap for one finding). Operational errors/partial scans are separate failures; metrics then apply only to evaluated cases and `status=partial`, not to the full corpus. Diagnostics are not security FP. No inflated 46-rules × cases true negatives or accuracy claim.

Micro precision = TP/(TP+FP), recall = TP/(TP+FN), F1 = 2TP/(2TP+FP+FN), rounded to six decimals. Undefined denominator is JSON `null`, not 100%; F1 is `null` when all three counts are zero. Per-rule `positive_support` is the count of expected positive cases, `benign_exposure` is the number of evaluated benign cases, independent of support. Rule coverage is supported IDs / all registry IDs; unsupported semantic IDs are excluded from this default deterministic suite. Coverage is not recall. Small support does not prove generalization. Unit-test counts do not measure precision or recall. These scores describe **this corpus**, not Dragons' real-world accuracy.

The 1.1 baseline was 16 TP / 0 FP / 2 FN on 22 cases. Corpus 1.4 has 48 cases, 50 TP / 0 FP / 0 FN and 38/46 positive-ID support: all 37 default static IDs and the separately enabled local-feed TI ID. The five semantic and three OSV/provider IDs have **no positive benchmark support** in this offline mode; fake-provider unit tests can verify only integration behavior, not live model quality. The 1.4 development score is **not** comparable to a new independent test set; the original eight holdout cases still yield 4 TP / 0 FP / 0 FN, and two of their correctness assertions were added after observation. The category mismatch review established `PI-001=prompt-manipulation`, `EXEC-001=dangerous-execution`, `CRED-001=credential-access`, `EXFIL-001=data-exfiltration`; scanner categories were not changed to fit the old manifest. Cross-artifact path correlation is now represented by development-only directory examples; their behavior needs independent hard-negative and holdout validation. When corpus cases change, bump `corpus_version` and explicitly regenerate/review the baseline. The baseline does not replace ground truth. No timestamps, absolute machine paths, or timing data are persisted.

Schema 2 requires exhaustive `expected_findings` for positive IDs with category, artifact, line and evidence; source/sink and ordered paths/flows can be asserted where applicable. The *primary* TP/FP/FN unit is the exact expected occurrence: an ID at a wrong occurrence counts as one FP and one FN, with mismatch fields reported separately. Unexpected IDs count once per logical case, not per duplicate occurrence. Targeted `expected_absent` findings remain separate checks even when another ID is expected. `id_level` is diagnostic only, never added to occurrence TP. `field_coverage` reports **asserted / correct / mismatched / missing** denominators per location, evidence, category, source, sink and path/flow: omitted assertions are **unscorable**, not correct. A missing occurrence counts as missing for each asserted field; a wrong field on a paired occurrence counts as mismatched. For the research excerpt, source and sink are explicit, but no graph edges can be independently established from its two lines, so the path denominator is zero. TI matches (`DRAGON-TI-001`) are not scored as deterministic positives; this pilot has no licensed malicious feed and **does not evaluate TI matches**. Semantic model inference is also not evaluated; run the separate offline semantic *integration* benchmark for its own, non-real-world results. `fn_causes` is optional, reviewed **post-scan** root-cause metadata keyed by finding ID; it never changes a positive expectation or matching. The existing `DRAGON-EXFIL-001` detector previously required a linked sensitive read and explicit transfer. The research excerpt instead directs displaying a link whose query contains a named password placeholder; following it would disclose the password. Static parsing preserved this instruction, but behavior normalization emitted no observation for this source-to-link relationship. A bounded, same-placeholder link-query observation now covers this general behavior without treating mere URL coexistence as flow, without visiting the URL, and without reporting raw query values. The original literal source/URL expectation was separately corrected to semantic redacted source/sink labels (the published finding contract); positive ID, artifact, line and evidence condition stayed unchanged. No graph path is asserted by this two-line excerpt. The reviewed `source/sink modeling problem` remains recorded as historical FN metadata and is not counted when the occurrence matches. Unreviewed FP/FN causes remain `unclassified`; no inference is made from a good score. No precision threshold is used as a CI gate: the CI commands collect the pilot only, while schema 1 retains its established development gate. A partial scan is a failure, not a zero-FP success. For schema 2, terminal mode exits zero on a completed scan even with FN; JSON/baseline mode exits one for failed correctness assertions, but still prints measurements.

Schema 2 JSON includes corpus version, manifest SHA-256, Git scanner HEAD (the recorded source revision, not an attestation of an uncommitted worktree), logical case count, split metrics, occurrence mismatch reasons, field denominators, targeted negatives, FP/FN taxonomies, ground-truth `attack_class_coverage`, `unmapped_expected_ids`, and explicit TI/semantic status. Attack-class support is counted from **expected occurrences**, not actual findings: one occurrence may support more than one class, so class counts are neither independent cases nor accuracy scores. `unique_malicious_artifacts` de-duplicates scored malicious bytes by SHA-256 within each class (falling back to artifact path for synthetic in-memory tests); it is not prevalence. The fixed ID-to-class mapping covers the named categories; unmapped IDs are reported rather than silently dropped. Reference-only candidates never enter these counts. An all-benign corpus has no positive support: TP=0 / FP=0 / FN=0 and precision/recall/F1 are **undefined (`null`)**, not 100%. With no predicted positives, precision is `null` (zero denominator); with one positive ground-truth occurrence and zero detections, recall is 0 and the direct-count F1 is 0.
